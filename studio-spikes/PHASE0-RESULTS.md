# Phase 0 技術検証の結果(2026-11-13 完了)

測定環境: Surface(Core i7-1265U、メモリ 16GB、**Intel Iris Xe(内蔵 GPU)**)、Windows 11。
検証プログラムは `src/bin/` にあり、全て実際に動かして数値を取った。

## 結論(技術選定の変更)

| 領域 | 要件定義書 v0.1 の案 | 検証後の決定 | 理由 |
|---|---|---|---|
| GPU | wgpu(D3D12) | **Direct3D 11 に統一** | Windows SDK の DXC は SPIR-V を出せず、Forge の HLSL を wgpu で使う経路が塞がった。D3D11 なら UI・エフェクト・動画デコードが1つのデバイスで共有でき、コピーが要らない |
| UI | egui(eframe) | **egui + egui-directx11** | D3D11 で描いたテクスチャを、そのまま UI に表示できた |
| 動画の読み書き | FFmpeg | **Media Foundation(Windows 標準)を主に、FFmpeg は追加形式用の任意部品** | ダウンロード不要、ライセンス問題(LGPL・特許)を OS 側に任せられる、ハードウェア対応済み |
| 音声出力 | cpal(WASAPI) | **cpal(変更なし)** | 時間の基準として使えることを確認 |
| 3D | `gltf` + 自前描画 | **変更なし** | 骨アニメーション付き 10 万三角形で 0.27ms |
| 点・平面トラッキング | OpenCV か Rust 実装 | **Rust 実装(OpenCV 不使用)** | 点 0.42px、平面の四隅 0.34px の精度が出た |
| 人物の検出・姿勢 | ONNX Runtime + DirectML | **ONNX Runtime(`ort`)。既定は CPU 実行、GPU は選択式** | この内蔵 GPU では CPU の方が速かった。モデルのライセンスは要確認(§9) |

## 個別の結果

### 1. D3D11 で UI とエフェクトを同時に描く(`ui_d3d11`)
- egui の画面に、毎フレーム VHS エフェクトをかけた 1920×1080 の映像を表示 → **60fps で安定**。
- エフェクトだけの描画時間: **1 回 0.41ms**(60fps の予算 16.7ms の 2.5%)。内蔵 GPU でも余裕がある。
- エフェクトの出力テクスチャを、コピー無しで UI に登録できた(`register_user_texture`)。

### 2. 音声クロック(`audio_clock`)
- 出力: WASAPI、48kHz・ステレオ・f32。バッファ 480 フレーム = **10ms ごとにコールバック**(最大 18.6ms)。
- コールバックから実際の発音までの遅延: **平均 31.4ms**(映像の表示をこの分だけ遅らせて合わせる)。
- 11 秒で、音声の標本数から計算した時間と実時間の差は **+0.2ms(18ppm)**。
  → 実時間の時計とは少しずつずれるので、**再生中の時刻は音声側の標本数から決める**設計が必要(要件どおり)。

### 3. 動画の書き出し・読み込み・シーク・音ズレ(`mf_video`)
1920×1080・30fps・20 秒の H.264+AAC で測定。

| 項目 | 結果 | 基準(要件) | 判定 |
|---|---|---|---|
| 書き出し(ハードウェア) | 1.33 秒 = **実時間の 15 倍速** | 1 倍以上(NFR-105) | ○ |
| 読み込み(GPU デコード) | **1219 fps** | — | ○ |
| シーク(目的のフレームが出るまで) | 中央値 **53ms**、最大 120ms | 100ms 以内(NFR-102) | △ 最大値が超える。キーフレーム間隔が長い素材ではさらに遅くなる → プロキシ(全フレームがキーフレーム)で対応 |
| 中身(フレーム番号を埋め込んで照合) | 600 中 **600 一致**、取りこぼし 0 | — | ○ |
| 音ズレ(白フラッシュとビープ) | 平均 **+0.5ms**、最大 10ms | 1 フレーム(33ms)未満(NFR-106) | ○ |

### 4. この PC で使える形式(`mf_codecs`)
| 形式 | 読み込み | 書き出し(ハードウェア) |
|---|---|---|
| H.264 / HEVC / VP9 | ○ | ○ |
| AV1 | ○ | ○ |
| AAC / MP3 / FLAC / ALAC | ○ | ○(Opus は読み込みのみ) |

- 読み込みの「ハードウェア 0」は表示上のもので、標準デコーダが内部で GPU(DXVA)を使う。速度(1219fps)で確認済み。
- ProRes、WebM の一部、古い形式などは Media Foundation で読めない可能性がある → 必要になったら FFmpeg を任意部品として追加。

### 5. glTF の 3D 描画(`gltf_render`、モデルは `make_gltf.py` で生成)
- 骨2本・アニメーション付きの glTF を `gltf` クレートで読み込み、GPU スキニングで D3D11 描画、背景へ合成。
- 0 / 0.5 / 1 秒の姿勢が期待どおり(0.5 秒で手前へ、1 秒で横へ曲がる)であることを画像で確認。
- 描画時間(1920×1080、深度あり、骨の計算と転送込み):
  - 1,536 三角形: **0.18ms**
  - **102,400 三角形: 0.27ms**(VRoid 程度のキャラ 1 体 = 数万〜10 万三角形なので、内蔵 GPU でも余裕)
- まだやっていないこと: テクスチャ、PBR・影、VRM の拡張(表情・揺れもの)、複数メッシュ。読み込みと描画の基盤は成立。

### 6. 点トラッキング(`klt_track`、外部ライブラリなしの Rust 実装)
ピラミッド Lucas-Kanade(4 階層、窓 15×15)。正解が分かる合成映像(1280×720、300 フレーム、
カメラが最大 ±260px 移動・±7° 回転・±12% 拡大縮小、ノイズあり)で測定。

| 項目 | 結果 |
|---|---|
| 1 フレーム間の誤差 | **0.01〜0.09px** |
| 300 フレーム連続追跡の誤差 | 平均 **0.42px**、95% 点 0.92px、300 フレーム目 0.66px(ドリフトは小さい) |
| 速度(リリースビルド、CPU 1 スレッド) | 1 点 1 フレーム **0.16ms** → 30 点を 1 秒分(30 フレーム)で 0.14 秒 |
| 画面外へ出た点の扱い | 正しく終了(35 点中 20 点。カメラの移動で一時的に画面外へ出たもの) |
| 場面の切り替え(カット)の検出 | 35 点中 **31 点**を見失いと判定(4 点は誤って追跡を継続) |

- **OpenCV は不要**と判断。点トラッキングは Rust 実装で実用精度が出た。
- 途中で分かったこと: 模様の弱い場所(ぼやけた背景)ではノイズに負けて誤差が数 px になる。
  → **追跡点は「角」になっている場所を自動で選ぶ**(最小固有値が大きい点)。UI でも、指定した点の近くの追跡しやすい点へ吸着させる。
- 改善が必要: カット検出の取りこぼし(往復チェックと組み合わせる)、回転・拡大縮小が大きいときのテンプレート更新、並列化。

### 7. 平面トラッキング(`planar_track`、Rust 実装)
平面内の「角」の点を約 200 個追跡し、最初のフレームとの対応から RANSAC でホモグラフィを求める。
点が減ったら現在の平面内から補充する。合成映像(1280×720、240 フレーム)で測定:
平面(ポスター)が立体的に ±34°・±14° 傾きながら移動・拡大縮小し、背景は別の動きをし、
フレーム 90〜170 では手前を物体が横切って平面の一部を隠す(`results/planar_frames.png`)。

| 項目 | 結果 |
|---|---|
| 四隅の誤差(4 隅の平均) | 平均 **0.34px**、95% 点 0.74px、最大 0.80px、最終フレーム 0.73px |
| 物体が手前を横切っている間 | 平均 0.27px、最大 0.74px(隠れた点は外れ値として除かれた) |
| 推定できなかったフレーム | 0 |
| 速度 | 28.5ms/フレーム(CPU 1 スレッド)→ 並列化で 1 フレーム数 ms を見込む |

### 8. 人物の検出と姿勢推定(`pose_onnx`)
OpenMMLab の RTMDet-nano(人物検出、4MB)と RTMPose-m(17 関節、52MB)を ONNX Runtime で実行。
COCO の公開画像(スキーをする人)で確認(`results/pose_skier.png`)。

- 人物の枠(スコア 0.90)、17 関節すべてが正しい位置に出た(目視)。信頼度は 0.61〜1.0。
- 速度(前処理込み):

| 実行先 | 人物検出 | 姿勢推定(1 人) |
|---|---|---|
| CPU | **13.5ms** | **19.5ms** |
| DirectML(Iris Xe) | 16.0ms | 31.6ms |

- 1 人なら CPU で約 30fps。解析はバックグラウンドで行うので、長い動画でも実用的。
- 配布サイズ: 実行ファイルに ONNX Runtime が静的リンクされて約 23MB、DirectML.dll 18MB、モデル 56MB。
- ONNX Runtime の利用状況送信(テレメトリ)は無効にした(外部送信しない方針)。
- まだやっていないこと: 複数人の追跡(フレーム間の対応付け)、人物の切り抜き(マスク)、手・顔。

## Phase 0 のまとめ

- 要件定義書 §3.1 の技術選定を、上の「結論」の表のとおり確定した。
- **この PC(内蔵 GPU)でも、2D エフェクト・3D・トラッキング・人物推定はすべて実用速度**で動く。
- 性能目標(NFR)は、この PC を「最低動作環境」として扱う。
- 残る確認: 実写映像でのトラッキング、姿勢モデルのライセンス、複数人の追跡と人物の切り抜き(Phase 7 で)。
- 空き容量: 作業後 約 5GB。ビルドの一時ファイルが大きいので、ビルド出力は定期的に消す。

## 注意: この PC の制約
- **空き容量が約 7.7GB しかない**。Rust のビルドだけで数 GB を使う。ONNX Runtime・OpenCV・モデルを入れると足りなくなる可能性が高い。
- **内蔵 GPU(Iris Xe)**。2D エフェクトは十分速いが、3D と人物推定(AI モデル)は重くなる見込み。性能目標(NFR-101)はこの PC を基準に引き直す。
